# 文风指南

## 调性核心

> 用户自己定的调子：**「不教育、不端着，让自己回头看觉得酷、让读者觉得我酷」**

把这句话当作所有写作判断的锚点。每一句话写完问自己：

- 这句话是在**教育**读者吗？→ 改
- 这句话听起来很**端着**（学术腔 / 自我吹捧）吗？→ 改
- 这句话**酷**吗？→ 留
- 这句话让读者觉得**作者酷**吗？→ 留

## AI 腔负面清单（最高频被打回项）

用户对这条最敏感，多次原话打回："这段很 AI"、"你得用我说话的语气写"。下面是**实际被否过的构造**，写完逐句对照清除：

| ❌ AI 腔构造 | 为什么是 AI 腔 | ✅ 用户的糙口语 |
|---|---|---|
| `没有 X，没有 Y——就是 Z` | 排比三连 + 破折号亮底，太工整 | `没什么契机，就是手痒——爱折腾` |
| `再往下一层：…` / `想通这一层` / `根上都是这一条` | 论文式层层递进连接词 | `那再问一句：…` / `就这点事` / `都从这儿来` |
| `按理我该…，但…` | 造作的让步转折 | `上次我还有点心虚，这次不解释了` |
| 破折号当戏剧反转用（每段都来一发） | 节奏拿腔拿调 | 多用句号断开，平铺直叙 |
| `不是 A，是 B`（连续排比） | 对仗腔 | 偶尔用可以，别连用；改陈述句 |
| `这意味着 / 本质上 / 某种程度上 / 值得一提的是` | 过渡 / 总结套话 | 直接说结论，删过渡词 |
| `经过深思熟虑 / 优雅地 / 一举` | 自我拔高 | 删，换具体动作或数字 |

**判据**：一句话如果"工整、对仗、有总结腔、读着像技术分享稿"——就是 AI 腔，拆成短句、加口语词（`就`、`反正`、`其实`、`得`、`哈`）、允许不对称。宁可糙，不要顺得发腻。

## 人称与视角

| 用 | 不用 |
|---|---|
| 我 | 我们 |
| 我做了 X | 实现了 X |
| 我把它改了 | 它被改了 |
| 我让 Claude... | Claude 协助我... |

**第一人称，主动语态**。博客是个人记录，不是产品文档。

## 句长与节奏

- **短句开头**：第一句话最好短小有力。例："上一篇之后，墨水屏在桌角稳稳跑着。"
- **长短交错**：技术段落可以长，体感段落必须短。
- **段落 3-5 句**：超过 5 句要考虑拆段或换小标题。
- **小标题要短**：用动词或名词短语，避免完整句子。
  - ✅ "第一拐点：浏览器预览就糊了"
  - ❌ "我是如何发现 Satori 不适合墨水屏的渲染过程"

## 技术细节的处理

### 出场原则

技术细节是**配菜**，不是主菜。出场理由必须是：

1. **支撑叙事**（"凌晨 02:03 commit pivot，睡了"）
2. **展示判断**（"SVG 光栅化是死结——浮点 Bezier 没 hinting"）
3. **承认局限**（"FreeType MONO 到今天我还说不清"）

不要为了凑字数堆术语。

### 术语处理

- **不教学**：术语直接用，不加"（一种 X 的技术）"括注
- **不全译**：行业通用英文术语就用英文（PR、commit、daemon、squash），不强行译成中文
- **关键术语解释一次**：第一次出现可以一句话说明语境，但不展开

### 代码块

- **短代码示例 OK**：5-15 行展示语法或结构最好
- **不要贴整文件**：超过 30 行的代码块要重新审视——这是博客不是 README
- **管线图 / ASCII art** 很有效果——展示数据流，比文字描述好读

## 让读者觉得作者"酷"的几个技巧

### 1. 老实交代 AI 参与度

❌ "我做了这个项目"
✅ "代码我没逐行看过，Claude 改完跑通了我就过——边角项目，行就行，不行回滚"

### 2. 老实交代失败 / 局限 / 走过的弯路

❌ "经过深思熟虑的架构设计..."
✅ "这是为情怀绕的弯。说实话我也没那么需要一个桌面小屏幕——这事从一开始就是为玩而玩"

### 3. 老实交代知识边界

❌ "我深入研究了 FreeType 的字体光栅化算法..."
✅ "FreeType MONO 这词儿我到现在还说不清"

### 4. 用具体的小细节代替形容词

❌ "性能大幅提升"
✅ "热路径从 400ms 掉到 10ms 一页"

❌ "这是个不错的方案"
✅ "凌晨 02:03 commit pivot，睡了"

### 5. 把场景写实

❌ "在工作之余完成的项目"
✅ "工作 Claude 一个 session、树莓派 Claude 另一个 session，挂着用。下午某个空档..."

## 真实例子对照

### 例 1：起头

**❌ 教科书式开头**：
> 本文将介绍如何使用 JSX 在墨水屏上实现 UI 渲染。我们将从需求分析开始...

**✅ 用户实际风格**：
> 上一篇把 Pi Zero 2W 翻出来玩起来之后，墨水屏在桌角稳稳跑着——每分钟看一眼时间和电量挺顺。但代码我一直没翻开过：那是一坨 imperative PIL，逐行 `draw.text((x, y), ...)`、逐个图标用几何函数自己画。

### 例 2：技术决策

**❌ 端着的写法**：
> 综合考虑性能、可维护性等因素，我们决定采用 Yoga 作为布局引擎，配合 PIL FreeType MONO 进行像素级精确渲染。

**✅ 实际风格**：
> 我跟 Claude 说"模糊"。它说是字体渲染问题。我顺着想：那干脆别走 SVG 这一步——既然 PIL 已经在 Pi 上跑得好好的，不如保留 PIL 当底层，上层用 vnode 树描述布局。
>
> 布局这一层我顺手把 Yoga 拉进来——Yoga 是 React Native 的底层布局引擎，Facebook 开源的 C++ flexbox 实现。我从 RN 业务里听说过这个名字，仅限于"知道它是干嘛的"——这次现学现卖。

### 例 3：反思

**❌ 假装完美**：
> 这套架构兼顾了开发体验和运行效率，是当前场景下的最优解。

**✅ 实际风格**：
> 诚实说，**部分是**。代码量从 566 行单文件 PIL 涨到 ~1500 行 + 一整个 Node 栈。Pi Zero 2W 512MB RAM 上多塞了 Node 进程 + Python daemon + Hono server。链路：数据要走 HTTP 才能变 PNG，多了一条故障线。
>
> 为什么没走更简单的 yoga-py + Python DSL？因为我**就是想用 JSX**——这是 ergonomics 偏好，不是技术需要。

### 例 4：AI 参与度的交代

**❌ 藏着掖着**：
> 在 AI 辅助下完成了这个项目。

**✅ 实际风格**：
> **最后老实交代**：这篇博客也是 Claude 写的。我做了一轮采访（它做编辑，问我"睡前为啥起念"、"切到 Claude 那 7 小时具体怎么发现糊的"、"两个 AI 怎么分工"），过了一遍大纲，给了写作调子，然后由它落地成你看到的这些字。我做了几处事实校正，定了标题。
>
> 写博客也是 AI 应用嘛。

## 段落结构的常用模式

### 三句法（讲一个小要点）

1. 一句话陈述（带细节）
2. 一句话解释 / 展开 why
3. 一句话承认局限或转折

例：
> Python 进程 daemon 化，第一版每次渲染 `spawn` 一个新 Python 进程，冷启 ~370ms（字体加载占大头）。改成 daemon 模式后，Node 端建一条长连接：请求一行 JSON、响应 `OK <len>\n` + 字节 PNG。热路径从 400ms 掉到 **10ms 一页**。

### 转折法（讲挫败 → 启发）

1. 我以为 / 我尝试了 X
2. 但 X 不行（具体原因）
3. 于是我（改成 / 想到）Y

### 老实话法（结尾或某段反思）

1. 直接承认尴尬 / 局限
2. 自嘲一句
3. 但还是肯定某个值

例：
> 代码我也没逐行审过。Claude 改完跑通了我就过——边角项目，行就行，不行回滚。

## 当用户调子跟标准模板不同时

**优先用户调子**。这里写的是用户**目前**的调子，但人是会变的。如果用户在采访里反复说"我想严肃一点写"、"这次想偏教程"，按用户意图来。

不过即便偏教程，**也要保留**：
- 第一人称
- 不假装客观（"在我看来"、"我倾向"）
- 真实的失败和迷茫片段
